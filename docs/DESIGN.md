# 設計メモ

## 何を直したのか

v1 は「1リポジトリ = 1人分の趣向」という構造だった。`build.py` がビルド時に
`interests` を掛けてスコアを確定させ、`news.json` に並び順まで焼き込んでいたので、
趣向を変えるにはリポジトリを変えるしかない。フォークして使ってもらう以外の
配布方法が原理的に存在しなかった。

v2 で変えたのは1点だけ。

> **客観的な信号の収集（GitHub Actions）と、主観的な並べ替え（ブラウザ）を分離する。**

ビルドが出すのは、誰にとっても同じ値だけ:

| 信号 | 意味 |
|---|---|
| `published_at` / `dated` | 公開時刻。`dated: false` は初回発見時刻での代用 |
| `first_seen` | このシステムが最初に見つけた時刻（NEW判定に使う） |
| `hatena` / `hatena_delta` | はてブ累計数と前回ビルドからの増分 |
| `cluster` | 同じ話題をまとめるためのキー |
| `reach` | **その話題を何媒体が報じたか** |
| `tier` | ソースの性質（`wire` / `media` / `search` / `social`） |
| `site` / `source` | 媒体名と、どのソース経由で来たか |

「どれを上に出すか」は `app.js` が localStorage の設定で決める。この分離のおかげで、
配信物は1つのまま、何人が何通りの趣向で使っても成立する。DBもログインも要らない。
設定が端末から出ないので、プライバシー保護がデフォルトになるという副次効果もある。

## 全体像

```
GitHub Actions（毎時）           静的配信                    ブラウザ
─────────────────────          ──────────                 ──────────
catalog/index.json
catalog/packs/*.json
        ↓                       dist/index.json    ─┐
  収集・正規化・重複排除          dist/p/<pack>.json ─┼→ 購読パックだけ取得
  客観信号だけ付与                                   │        ↓
        ↓                                          │   localStorage の設定で
  data/state.json（Actions Cache）                   │   スコア計算・並べ替え
                                                    │        ↓
  functions/api/*  ←──────── ユーザー追加ソース ──────┘   クリックでサイトと話題を学習
```

## TOPの作り方（`app.js`）

### なぜ作り直したか

最初の版は「鮮度 × 興味キーワード × はてブ数 × サイト嗜好」の1本のスコアで並べ、
TOPだけを「話題 / あなた向け / 新着」の3セクションに切り分けていた。実際に使うと
2つの問題が出た。

1. **癖の強い個人ブログが上に来る。** はてなブックマーク数は「ネットで語りたく
   なる度」を測る指標であって、「重要度」ではない。しかも `hot` パックが
   はてブのランキングをそのまま母集団に流し込んだうえで、スコア式が同じはてブ数で
   もう一度押し上げていた（二重計上）。ランキング上位が構造的に意見記事・エッセイに
   偏るので、これは仕組み上の必然だった。
2. **興味のない記事が多い。** 興味キーワードを設定していないユーザーは
   `interest` が 1.0 で固定され、実質「鮮度 × はてブ」に退化する。学習していたのは
   サイト単位の嗜好だけで、話題は学習していなかった。

### 直したこと

**はてブを捨てたのではなく、重要度の判定から外して話題度の弱い信号に降格した。**
代わりに「誰もが知るべきニュースか」の判定には、**同じ話題を何媒体が報じたか**
（`reach`）を使う。これは客観的で、しかも個人ブログには原理的に効かない
（他社が同じ話題を報じない限り `reach` は 1 のまま）。信号自体は最初から
`cluster` として持っていたのに、スコアに使っていなかった。

TOPは3つのレーンを別々に選び、見出しで区切らずに `MIX_PATTERN` の比率で
織り交ぜて1本のリストにする。

| レーン | 何を選ぶか | 使う信号 |
|---|---|---|
| `big` | 誰もが知るべきニュース | `reach`（3媒体以上）× 鮮度（半減期20時間）× `tier` |
| `you` | 興味に基づくおすすめ | 興味キーワード + 学習した話題 + サイト嗜好 |
| `new` | 購読ソースの新着 | 鮮度（半減期8時間）× サイト嗜好 × `tier` × はてブ |

どのレーンから来たかは、セクション見出しではなくカード内の小さなラベルで示す。

- **`tier`**: ソースの性質ごとの信頼度（`TIER_AUTHORITY`）。はてブのランキング
  経由（`social`）を低く置くのが、「癖の強いブログがTOPを占める」に対する直接の
  効き手になる。ランキングそのものは「話題」タブに残るので、見たい人は見られる。
- **学習**: 記事を開くとタイトルから話題の語を拾って重みを育てる（`learnFrom`）。
  古い語は開くたびに薄れるので、興味が変われば入れ替わる。何を覚えたかは
  設定画面に出して、いつでも消せるようにしてある。詳しくは
  「[話題の語をどう決めるか](#話題の語をどう決めるかappjs)」。
- **既読の抑制**: 一覧に出した記事は覚えておき、次に開いたときスコアを 1/4 にする。
  無限スクロールと再訪で同じ顔ぶれが並ぶのを防ぐ。
- **多様性**: 同じサイトが1件増えるごと、同じ話題が1件増えるごとにスコアを
  割り引く（貪欲MMR）。
- **無限スクロール**: 20件ずつ描き足す。購読ぶんの在庫を使い切ったら、購読して
  いないカテゴリを1つずつ読み込んで継ぎ足す（購読は勝手に増やさない）。

チューニング定数は `app.js` 冒頭にまとまっている。回帰テストは
`tools/rank_smoke_test.js`（DOMをスタブして `window.__msn` を叩く）。

## 話題の語をどう決めるか（`app.js`）

自動で覚えた話題は、最初は「見出しを正規表現で切って、先頭3語を覚える」だけ
だった。実際に使うと、覚えた語の半分近くが話題として使いものにならなかった。

| 出た語 | 何が起きていたか |
|---|---|
| 生成 / 提携 / 提供開始 / 仕事 | 単体では意味の定まらない文脈語。どの記事にも当たるので、おすすめの絞り込みに効かない |
| 倍違 / 児出産 / 頭身 | 語ですらない。漢字の連なりを機械的に切った事故（「1.5倍違う」「第2児出産」「8頭身」） |
| itmedia / ビジネスオンライン | 媒体名。見出しに紛れ込んでいたものを話題として覚えていた |
| 設計初期 | 1本の見出しかぎりの言い回し。二度と当たらない |

**欲しいのは「その人が本当に興味を持っている分野」で、それは1本の見出しからは
決まらない。** そこで、拾う段階と覚える段階を分けた。拾う側は候補を広めに出し、
語として成立しているかどうかは後段の3つの関門で決める。

### 1. 境界の補正（`candidateWords`）

形態素解析器は入れない（依存を増やしたくないし、ブラウザで動かす）。かわりに、
**漢字の連なりの前後1文字**を手掛かりに、切り出しの事故を潰す。

- **数字の直後の漢字は助数詞**。語の頭に残すと語でなくなる。
  「第2児出産」→ `児`を落として `出産`、「3社連合」→ `連合`、「8頭身」→ 捨てる。
- **送り仮名が続く漢字は動詞・形容詞の語幹**。「1.5倍違う」の `倍違` は
  末尾の `違` を落として1文字になり、消える。「値上げ」の `値上` も同じ。
  助詞（は・が・を・に・へ・と・で・も・の・か・や）と重なる仮名は使わない。
  サ変の「し」も使わない（「提携し」の `携` は名詞の一部）。
- **長すぎる漢字の連なりは捨てる**（`KANJI_MAX`）。「経済産業省総合資源調査会」は
  複数の語の合成で、どこで切っても事故になる。他の語で拾えるので捨てるほうが安い。
- **隙間なく並んだ2語は連結したものも候補にする**。「生成」＋「AI」→ `生成ai`。
  単体では文脈語でも、連結すれば話題を指すことがある。
- 英字2文字は大文字のときだけ拾う（`AI` `EU` は拾い、`of` `to` は拾わない）。

### 2. いま流れている見出しの統計（`corpusStats`）

**どの見出しにも出る語かどうかは、手書きの除外リストではなく実データで決める。**
手元に読み込んである見出し全部を母集団にして語ごとの出現記事数（DF）を数え、
`COMMON_DF_RATIO`（2%）を超える語は覚えない。「発表」「提供開始」「生成」は
ここで落ちる。除外リスト（`STOP_WORDS`）は、統計が効くまでの立ち上がり用に
最小限だけ残してある（`CORPUS_MIN_DOCS` 件に届くまではこちらが効く）。

同じ統計から「珍しさ」も出て、これが2つの用途を持つ。

- **1つの見出しから覚える語を選ぶ順番**。以前は先頭3語だったので、頭に置かれ
  がちな媒体名や定型句を優先的に覚えていた。位置ではなく珍しさで選ぶ。
- **重みの伸び幅**。ありふれた語ほど、当たっても重みが伸びない。

ただし珍しさだけで選ぶと、**切り出しの事故がいちばん珍しい語になって枠を食う**。
そこで、他の見出しに一度も出ていない語は割り引く（`UNATTESTED_PENALTY`）。
クリックした記事自身は母集団に入っているので、DFが1では裏付けにならない。

媒体名は、見出しから媒体名の文字列そのものを抜いてから切り出す（`withoutSite`）。
「◯◯（ITmedia ビジネスオンライン）」形式の見出しはこれで消える。抜けたぶんも、
媒体名は多くの見出しに出るのでDFで落ちる。

### 3. 2回目の確認（`absorb`）

初めて見た語はいったん様子見（`settings.candidates`）に入れ、**別の記事でもう
一度出てきたときだけ**「覚えた話題」に上げる。1本の見出しかぎりの言い回し
（`設計初期`）も、統計をすり抜けた文脈語も、2回目が来ないのでここで消える。

「別の記事で」が肝で、同じ記事を開き直しても2回目としては数えない。様子見は
`CAND_TTL_DAYS` で期限切れになるので、たまたま出ただけの語は溜まらない。

覚えるまでに1回ぶん遅れるが、**間違った語を覚えて消してもらうほうがコストが
高い**（消すには設定画面を開く必要があり、そこまで気づかれない）。

### 似た語をまとめる

以前は語ごとに独立した重みを持っていたので、「生成」と「生成AI」を別々に覚えて
二重に効かせていた。同じものを指す語（漢字混じりは包含、英字とカタカナは前方
一致で判定）は1語にまとめ、**絞り込みに効くほう＝見出し全体で珍しいほう**を残す。

ただし、どこにも裏付けのない語は採らない。「bim」と、連結でできただけの
「bim連携」なら `bim` を残す。前者は他の見出しにも出ているが、後者はその見出し
にしか存在しない。

### 何が残るか

同じ見出しサンプルを通すと、`生成` `提供開始` `提携` `仕事` `成果` `itmedia`
`ビジネスオンライン` `倍違` `児出産` `頭身` `設計初期` は残らず、`大林組`
`openai` `claude` `cursor` `アップル` のような、それだけで分野を指す語が残る。

回帰テストは `tools/rank_smoke_test.js` に、上の事故を実例のまま入れてある。

## 話題のまとめ方（`build.py`）

`reach` を数えるには、各社が別の見出しで報じた同じ事件を1つにまとめる必要がある。
以前のクラスタキーは正規化タイトルのハッシュ（完全一致）だったので、見出しが
1文字でも違えば別の話題として数えていた。

形態素解析器は入れない（依存を増やしたくない）。文字バイグラム集合の Jaccard 係数で
近似し、共有バイグラム数と係数の両方に下限を置く。**しきい値は見出しの長さで
変える**。短い見出しは1語違うだけで別のニュースになるが（「首相が訪米へ」と
「訪中へ」）、長い見出しは各社が言い換えても十分な量が一致するため。

### 文字の一致だけでは足りない

文字バイグラムだけで見ると、**主語が違うだけの別ニュースが7割方一致してしまう**。

```
「トヨタ、新型EVを来春発売へ」 と 「ホンダ、新型EVを来春発売へ」  → 一致率 0.60
「大林組が新型ロボットを発表」 と 「鹿島が新型ロボットを発表」    → 一致率 0.64
```

まとめ不足は `reach` を取りこぼすだけだが、まとめすぎると**別のニュースが一覧から
消える**。害の大きさが違うので、固有名詞の一致を重く見る2つの規則を足した。

固有名詞は辞書ではなく統計で見つける。文字種の切り替わりを語の切れ目とみなして
内容語を切り出し（「大林組が新型ロボットを発表」→ 大林組 / 新型 / ロボット / 発表）、
**同じビルドに入った全記事のうち出現率が低い語**を「その話題に固有の語」とする。
「発表」「開始」のようにどの見出しにも出る語は自動的に外れる。

1. **互いに相手にない固有名詞があれば、似ていても別の話題**（トヨタ / ホンダ）。
   語の一致ではなく相手の見出しの中に見つかるかを見るので、「首相」は「石破首相」に
   含まれるものとして扱う。漢字は語がくっつくため（「連携の新機能」と「連携機能」）、
   文字のつながりが半分より多く相手にあれば同じものを指しているとみなす。
   半分ちょうどでは足りない ——「JR東日本」と「JR西日本」は「日本」だけを共有する。
2. **同じ固有名詞を共有していれば、言い換えの証拠として下限を下げる**（0.44 → 0.34）。
   「日銀が追加利上げを決定」と「日銀、追加利上げを決定 政策金利0.75%に」は
   文字の一致率が 0.42 しかないが、これは同じニュースである。

さらに、**1つのクラスタは同じ媒体の記事を2件以上飲み込まない**。数えたいのは
「何媒体が報じたか」なので同じ媒体の2件目には意味がないし、定型の見出しを量産する
サイトがあると、そのサイトの記事がまるごと1件に潰れて一覧が痩せてしまう。

見出し30組（同じ話題15組・別の話題15組）で見た挙動:

| | 同じ話題をまとめた | 別の話題を混ぜた |
|---|---|---|
| 文字バイグラムだけ | 9 / 15 | **10 / 15** |
| 固有名詞の規則あり | **14 / 15** | **0 / 15** |

残っている取りこぼしは、大きく言い換えられて固有名詞も共有しない見出し
（「石破首相が所信表明演説」と「首相の所信表明演説 全文」）。`reach` を
取りこぼすだけで記事自体は一覧に残るし、本当に大きなニュースは媒体数が多いので、
どこかで3媒体は揃う。

## 同じ話題を開く（`app.js`）

`merge()` はクラスタごとに代表1件だけを一覧に出す。畳んだ記事は捨てずに
`dupes` として持たせ、カードの下に**たたんだ状態で**添える。

```
政府が建設DXの支援制度を発表 中小企業も対象に
共同通信  21分前  NEW  3媒体
─────────────────────────────
日本経済新聞・NHK も報じています              ▾
```

件数ではなく**媒体名**を出す。「他2件」より「NHKも報じている」のほうが、開くか
どうかの判断に使えるため。3媒体以上なら「A・B ほかN媒体」に畳む。

カードは全体が1つのリンクなので、開閉ボタンはカードの外に置いて縦に積んである
（`a` の中に `button` は入れられない）。ミュートしたサイトと、代表と同じ媒体の
2件目は、開いた一覧にも出さない。

## カタログ = みんなで育てる部分

`catalog/` がこのプロジェクトの共有資産で、ここだけが人手の対象。

```
catalog/index.json          パック（カテゴリ）の一覧とメタ情報
catalog/packs/<id>.json     そのパックのソースと推奨キーワード
```

ソースは3種類:

| type | 用途 | 得られるもの |
|---|---|---|
| `rss` | 媒体の公式RSS | サムネイル・正規URL・はてブ件数が揃う |
| `html` | RSSのないサイト | スクレイピング。公開日時は取れない |
| `query` | Googleニュース検索RSS | 未登録サイトを含む網羅。画像とはてブは無し |

ソースには任意で `tier` を書ける。省略すると `query` は `search`、それ以外は
`media` になる。`wire`（通信社・公共放送）と `social`（ソーシャルブックマークの
ランキング経由）は明示が必要で、ここが TOP の重み付けに直接効く。

パックは `suggested_interests` を持てる。購読したときにユーザーの興味キーワードへ
未登録のものだけ取り込まれる。**キュレーションした人の勘所がプリセットとして配れる**
のがこの仕組みの狙いで、v1 でハードコードされていた BIM/Revit の重みは
`catalog/packs/construction.json` の推奨キーワードに移した。

### なぜ最初から27カテゴリ用意したのか

「みんなで育てる」は目的としては正しいが、**育つ前に人がいなくなる**という
順序の問題がある。最初のカタログは作者の関心（建築とIT）そのままの11カテゴリで、
既定で選ばれるのが `話題 / 総合 / IT・テック / AI` の4つだった。これだと
初めて開いた人が最初に見るのは技術記事の一覧で、「自分向けではない」と判断されて
終わる。カテゴリを足してもらう以前に、足したいと思う人が残らない。

そこで方針を逆にした。

> **カタログは「作者が読みたいもの」ではなく「誰が来ても最初の1画面で
> 自分の居場所が見つかる」ように並べる。専門分野はその中の1つとして置く。**

具体的にやったこと。

- **全27カテゴリに広げた。** ニュース（総合・話題・国際・政治・地域と防災）、
  生活（経済・マネー・仕事・暮らし・グルメ・旅行・子育て・健康）、
  趣味（エンタメ・アニメ・ゲーム・スポーツ・クルマ・ファッション・
  ペット・本・デザイン）、技術（IT・AI・開発・科学・建設）。
  技術系は27のうち5で、これがだいたい妥当な比率だと思う。
- **既定を7カテゴリに広げた**（総合・話題・経済・IT・暮らし・エンタメ・スポーツ）。
  一般紙を開いたときの面構えに近い。専門カテゴリは既定から全部外した。
- **並び順を「読者にとっての近さ」にした。** ニュース → 生活 → 趣味 → 技術。
  以前は建設が7番目にあったが、いまは末尾。順番はそのまま設定画面の
  スクロール順で、上にあるものほど選ばれるので、ここは中立に保つ必要がある。
- **推奨キーワードの重みを下げた。** 詳細は次項。

### 推奨キーワードが効きすぎていた

`suggested_interests` は購読時にユーザーの興味キーワードへ取り込まれる。
ここに落とし穴があって、**取り込まれた語はそのパックの中だけでなく TOP 全体に
効く**（`score()` はタイトルの部分一致を見るだけで、記事がどのパックから来たかを
見ていない）。

初期の `construction.json` は `BIM: 2.0` `Revit: 2.0` `建設DX: 2.0` `CAD: 1.5`
`自動化: 1.0` を配っていた。建設を1つ足しただけでTOPの「あなた向け」レーンが
建設で埋まる、という状態になっていた。`自動化` に至ってはどのジャンルの記事にも
当たる。

いまの決まりは3つ。

- 1パックあたり2〜5語まで。
- 重みは 0.5〜1.2。1.2 は「そのジャンルの中心語」に限る。
- **短い語・どこにでも出る語を書かない。** 判定が部分一致なので、`AI` は
  「メイン」に、`本` はほぼ全部の記事に当たる。`生成AI` `保護猫` のように、
  それ自体で意味が決まる長さの語を選ぶ。

`ai.json` の `AI: 0.6` を `AI活用: 0.8` に替えたのはこの理由。

### ソースの選び方

新しいカテゴリの多くは専門メディアの公式RSSが見つからない。かといって
`query`（Googleニュース検索）だけで組むとサムネイルもはてブ件数も付かず、
実質「新着順」に退化する（後述）。そこで**どのパックも、まず落ちない土台の上に
専門ソースを載せる**構成にした。

| 層 | 何を置くか | ねらい |
|---|---|---|
| 土台 | Yahoo!ニューストピックス / NHK / Googleニュースのトピック / はてブのカテゴリ | 各社が編集済み。1つのURLで量が確保できる |
| 専門 | そのジャンルの媒体の公式RSS | サムネイルと固有URLが付く。ここがカテゴリの個性 |
| 補完 | `query` | 未登録サイトとロングテール |

土台が生きているかぎり、専門ソースが1つ死んでもそのカテゴリは空にならない。
逆にパックの記事が0件になった場合、`write_dist()` はそのパックを配信カタログ
ごと落とすので、**空のタブがユーザーに見えることはない**。

ソースは45件から116件になった。毎時の全件取得は逐次で、Googleニュース検索は
そのうち約50件。ここが将来詰まるならティア分割（Issue #11）の出番だが、
まだその段階ではない。

RSSの移転やセレクタのずれは「0件」として静かに進むだけでビルドは通ってしまうので、
`tools/check_sources.py` で全ソースを1件ずつ叩いて確認できるようにした。
外部サイトへ何十回も出ていくのでCIには入れていない（落ちても向こうの都合で、
こちらの回帰ではない）。

最初に流したとき、公式RSSがあると思っていた4本が落ちた。

| 落ちたソース | 症状 | どうしたか |
|---|---|---|
| Yahoo!ニュース ライフ | 取得できない（トピックスに「ライフ」の区分が無い） | 外した。NHK暮らし・はてブ暮らし・検索2本で足りる |
| ファミ通 / AUTOMATON | 取得できない（bot対策と思われる） | 外し、検索1本を足した。4Gamerとはてブゲームは生きている |
| 乗りものニュース | 取得はできるが0件（フィードを返していない） | 外し、おでかけの検索1本を足した |

**どのパックも空にならなかった**のは、土台（Yahoo!ニューストピックス・NHK・
Googleニュース・はてブ）と検索フィードが全部生きていたため。落ちたのは
「専門ソース」の層だけで、この二層構成が想定どおりに効いた形になる。


## 初めて来た人に何を見せるか

このアプリは開いた瞬間が一番不利になる作りをしている。中身は起動後に
JavaScript が描くので、**素の `index.html` には「何が読めるサイトなのか」を
示す文字が1つも無い**。そのまま来た人には真っ白な画面のあと設定シートが開き、
検索エンジンにはタブバーと「読み込み中…」しか見えない。人にも機械にも
同じ問題で、直し方も同じ ——「静的なHTMLに説明を置く」。

`index.html` の `#intro` がそれ。カテゴリを選ぶだけであること、重要度の決め方、
学習すること、設定が端末から出ないことを4点で書いて、その下に
**カタログから生成したカテゴリ一覧**（`build.py` の `pack_list_html()`）を
置いている。カテゴリを足せば説明も自動で増える。

見せる相手は「まだ設定を持っていない訪問者」で、これは初めて来た人と
クローラの両方を指す。2回目以降の人には要らないので、`app.js` は起動時に
`settings.onboarded` を見て `#intro` を `hidden` にする。**出し分けの条件が
「人か機械か」ではなく「初回か再訪か」**なのが大事なところで、クローラは
localStorage を持たないから自動的に初回側に入る。人と機械に違うものを
見せているわけではない。

設定シート側では、初回だけ `renderWelcomeSection()` を先頭に出し、
**カテゴリ以外の項目（キーワード・ミュート・持ち出し・バージョン）を全部隠す。**
初めての人に9セクション見せても読まれないし、決めてほしいのはカテゴリだけ。
完了ボタンの文言も「はじめる」に変える。

### 「完了」を探して上まで戻らせない

設定シートは項目が増え続ける画面で、カテゴリだけで27行ある。シート全体を
スクロールさせていたころは、下のほうを触ったあと「完了」を押すために
一番上まで戻る必要があった。トップページのタブバーと同じ考え方で、
**見出しと「完了」は動かさず、その下だけをスクロールさせる**（`.sheet` を
縦のフレックスにして、`.sheet-scroll` に `overflow-y` を持たせる）。

シート下端にもう1つボタンを足す手もあるが、それだと「どちらを押しても
同じ」ことを説明する必要が出る。押す場所は1つのまま、常に見えているほうを選んだ。

### SEO

やったのは最低限だけ。

| 項目 | 中身 |
|---|---|
| `<title>` / `description` | 「MySmartNews｜読みたいカテゴリだけのニュースリーダー」＋カテゴリ数入りの説明 |
| canonical / OGP / Twitter Card | 絶対URLが要るので `SITE_URL` から差し込む |
| JSON-LD | `WebApplication`（`NewsApplication` / 無料） |
| `robots.txt` / `sitemap.xml` | `build.py` が `dist/` に生成 |
| 本文 | 上記の `#intro`。実質これが本体 |

`{{SITE_URL}}` `{{PACK_COUNT}}` `{{PACK_LIST}}` の3つは `copy_static()` が
配信時に埋める。`SITE_URL` は環境変数で、既定は `https://mysmartnews.pages.dev`。
GitHub Actions 側は配信先（Cloudflare Pages / GitHub Pages）から組み立てる。
プレースホルダが残っていないことと robots / sitemap が出ることは
`tools/build_smoke_test.py` で見ている。

`og:image` はまだ無い。PWAアイコンと同じで画像アセットが要る（Issue #16）。

## Googleニュース検索RSSの位置づけ

「サイト登録が手動」を解く道具として有効だが、**主役にはしない**。実データで確認した
限界がある。

- サムネイル画像がまったく付かない
- リンクが `news.google.com/rss/articles/CBMi...` のリダイレクトURLで、実記事に
  付いたはてブ件数と結びつかない（`hatena` が常に 0 になる）
- ソースの品質が玉石混交

つまり Googleニュースだけで作ると、スコア式の「人気度」が常に 1.0 になり、実質
「新着順＋キーワード加点」に退化する。そこで二層に分けている。

- **品質レイヤ（`rss` / `html`）**: サムネイル・正規URL・はてブが揃う主要媒体。
- **網羅レイヤ（`query`）**: ロングテールと未知のサイト。

この非公式エンドポイントが壊れても、品質レイヤだけで動き続ける。差し替え点は
`build.py` の `KEYWORD_SEARCH_FEED` と `functions/api/search.js` の `SEARCH_FEED` の2箇所。

なお `query` は `site:example.com` も書けるので、RSSを持たないサイトを
スクレイパなしでフィード化できる（画像とはてブは諦めることになる）。

### 韓国語の記事を落とす

`hl=ja&gl=JP` で引いても、検索フィードは韓国メディアのハングルの見出しを混ぜて
くることがある。日本語で読めない記事が一覧に並ぶうえ、媒体名が「表示しないサイト」
にも溜まっていき、ユーザーが1件ずつチェックを入れて消す羽目になる。**媒体名で
ブロックリストを持つのではなく、文字種で落とす**（`build.py` の `is_korean()`)。

- 媒体名にハングルが入っていれば韓国語の媒体
- 見出しにハングルがあり、**かなが1文字も無ければ**韓国語の記事

かなを条件に足しているのは、日本語の見出しがハングルを引用しているだけのもの
（「K-POPの방탄소년단が新曲を発表」など）を巻き込まないため。手書きのリストと
違って、まだ見たことのない韓国メディアが検索フィードに現れても効く。

同じ判定は `app.js` にも置いてある。自分で追加したソース（プロキシ越しに
ブラウザが直接読むフィード）はビルドを通らないのと、すでに端末へ保存済みの
ミュート指定を掃除するため。

## ユーザーが自分で足すソース

ブラウザから `news.google.com` や各社のRSSを直接読むことはできない（CORSヘッダが
無い）。Cloudflare Pages Functions を薄いプロキシとして挟むことで解決している。

- `GET /api/search?q=<検索式>` … 検索URLはサーバー側で組み立てる。任意のホストには飛ばない
- `GET /api/feed?url=<RSSのURL>` … 内部アドレス・変なポート・非XMLを弾いたうえで中継

エッジで15分キャッシュする。GitHub Pages など Functions のない配信先では、
フロントが `/api/feed` の 404 を見てこの機能ごと隠す（他の機能は動く）。

## 表示側の変更をどう届けるか

配信物には記事データだけでなく `app.js` / `style.css` / `index.html` も入っている。
つまり **表示側の変更はニュースのビルドに相乗りして配信される**。

ここには落とし穴が2つあって、どちらも「直したはずの機能が出てこない」に化ける。

1. `Update News` ワークフローが毎時のスケジュールでしか動かないと、main に
   マージしても次の毎時ビルドまで反映されない。→ `push: branches: [main]` を
   足して、マージした時点で作り直すようにした。
2. `_headers` が `/app.js` を5分キャッシュするので、配信されていても
   ブラウザ側が古いものを掴んでいることがある。

2つ目は外から見て区別がつかないので、ビルドIDを両方に載せて突き合わせる。

- `build.py` が表示側ファイルのハッシュから7桁のIDを作り、`index.json` の
  `app_build` に載せる。
- 同じIDを、`dist/` へコピーする `app.js` の `var APP_BUILD = 'dev';` の行に
  焼き込む。
- `index.json` は毎回取り直され、`app.js` はキャッシュされる。両者がずれて
  いれば「古い app.js が動いている」と断定できるので、設定画面の「バージョン」に
  そのまま出す。

## 無料で回るのか

| 項目 | 制約 | 実際 |
|---|---|---|
| Cloudflare Pages 帯域 | 無制限 | 問題にならない |
| Cloudflare Pages ビルド数 | 500回/月 | `wrangler pages deploy`（Direct Upload）はこの枠を消費しない。毎時=730回/月でも通る想定 |
| Pages Functions | Workers 無料枠 10万リクエスト/日 | ユーザーが自分で足したソースだけが通る。カタログのパックは通らない |
| GitHub Actions | パブリックリポジトリは無料 | 毎時1回、45ソース程度 |
| リポジトリ肥大 | Pages のリポジトリ上限 1GB | **記事データをコミットしない**ことで解決。`dist/` は生成物、`data/state.json` は Actions Cache |

v1 は毎時 231KB の `news.json` をコミットしていた（年間 8,760 コミット）。これをやめたのが
スケール面で一番効いている。

`data/state.json` を Actions Cache に置けるのは、キャッシュの退避条件（7日間アクセスが
なければ削除）と `STATE_RETENTION_DAYS = 7` が一致していて、しかも毎時読むので実質
消えないため。キャッシュミス時は初回発見時刻が現在時刻になるだけで、ビルドは通る。
